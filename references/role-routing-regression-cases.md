# 主角色动态路由回归用例

这些用例用于检查岗位名称不会覆盖 JD 正文。输入为 JD，不使用候选人简历决定主角色。

## 用例 1：标题是用户运营，正文以增长为主

- 标题：用户运营
- 关键职责：制定拉新策略；拆解注册与付费漏斗；设计 A/B 测试；进行渠道归因；优化次日和七日留存；设计邀请裂变机制。
- 期望主角色：`user_growth`
- 期望相邻角色：`user_operations` 仅在正文另有用户承接、分层、社群、服务或复购证据时输出。
- 失败表现：仅依据标题输出 `user_operations`；把社群、服务等未出现的能力补入结果。

## 用例 2：标题是用户增长，正文以用户运营为主

- 标题：用户增长
- 关键职责：承接成交用户；维护会员社群；对新客、沉睡客和高价值用户分层；处理用户问题；推动复购、转介绍和 UGC 沉淀。
- 期望主角色：`user_operations`
- 期望相邻角色：`user_growth` 仅在正文另有拉新、漏斗、实验或归因证据时输出。
- 失败表现：仅依据标题输出 `user_growth`；把一般复购或社群活动自动推断成增长实验。

## 用例 3：增长与用户运营均形成完整闭环

- 标题：用户增长运营
- 关键职责：负责渠道获客和注册转化；设计实验并分析漏斗；承接新用户；实施用户分层、召回、社群活动和复购策略。
- 期望结果：根据原子要求得分和直接业务结果确定主角色；两者接近时输出混合角色或一主一邻，并展示各自证据与置信度。
- 失败表现：不展示依据而强行单选；同一条证据在两个角色中重复加分。

## 复核问题

每次变更岗位配置或评分规则后，至少检查：

1. 原始职责是否仍按 JD 顺序展示；
2. 主角色是否来自职责动作、对象、交付物和业务结果；
3. 岗位名称是否只用于召回候选配置；
4. 相邻角色是否达到区分性证据与阈值要求；
5. 简历排序是否随后服从主角色，而不是候选人原职位名称。
